1 项目概述

月结复核中，发现异常只是第一步：复核人员还要取得证据、判断原因，并证明拟议的调整不会改坏原始账簿。现有的 AI 财务工具多数直接给出结论，但结论依据了哪些资料、资料是否在当时可见、能否被第三方复核，往往说不清。

账证智核把每一次调查固定在账套、数据快照和规则版本上：确定性规则先做检查；调查只能读取当前快照中的证据；模型的建议不会自动成为业务事实；处理草稿由案件发现确定性生成，只进入隔离模拟并由程序逐分复算；迟到的资料生成新快照，旧复核失效，同一发现接续到新案件继续复核。项目在本地即可运行，不需要模型密钥就能完成完整的规则演示。

2 背景与需求

2.1 复核工作的真实痛点

  • 证据分散：订单、收货、发票、付款与分录分属不同系统，复核人员要逐笔回查来源。
  • 时点错位：迟到的单据会改变判断，但旧的复核意见往往没有随之失效。
  • 调整风险：调整分录一旦直接写入账簿，错误难以追溯；需要先在副本上验证影响。
  • AI 结论不可复核：通用大模型可以生成看似合理的解释，但无法保证引用真实存在、属于当时可见的资料。

2.2 政策依据

财政部《会计软件基本功能和服务规范》（财会〔2024〕12号，2025年1月1日起施行）对会计软件提出了与本项目设计直接对应的要求：

条款要求（摘要，以原文为准）本项目对应设计
第二十一条（二）（三）防止电子会计凭证重复入账；提供不可逆的记账功能，不得删除、插入或修改已记账凭证重复确认检测与冲回草稿；原始账簿只读，调整只进隔离模拟
第三十二条记录用户操作日志，可按操作人员、时间和内容查询审计记录、快照绑定与复核失效
第六条、第十八条遵循电子凭证会计数据标准，解析符合标准的电子会计凭证财政部数电发票标准样例的核验导入
第二十九条、第四十一条符合国家统一标准的数据接口，不得拒绝用户导出电子会计资料开放 API 与 Markdown/JSON 底稿导出
第三十八条鼓励提供个性化、自动化、智能化核算处理功能智能化在可核验的边界内进行

此外，财政部《会计信息化发展规划（2021－2025年）》（财会〔2021〕36号）以信息化支撑会计职能拓展为主线、以标准化为基础、以数字化为突破口，目标包括基本建立覆盖输入、处理、输出各环节的会计数据标准体系；国家税务总局公告2024年第11号自2024年12月1日起在全国推广数电发票。电子凭证进入账务后，如何在不改动原账的前提下自动复核、并让结论可追溯，是我们据此作出的需求判断。

条款与要求摘自官方原文（会计软件规范按财政部发布的 PDF 逐条核对；数电发票见国家税务总局规范性文件库；规划见国务院政策文件库附件）；“本项目对应设计”一列与上段需求判断属于本项目的推断，不是官方要求。

2.3 目标用户与场景

  • 会计实训与复核教学（首个可落地场景）：用财政部公开样例和标注明确的教学变体（如故意加入的重复凭证）组织练习，学生能看到每条结论的证据和失效规则。
  • 代账机构与企业财务的月结复核（目标场景）：在授权、脱敏的真实账套上试点，属于后续的外部验证，当前不宣称已取得业务效果。

3 技术架构

3.1 数据不变量

  • 金额全程使用 Decimal，接口以字符串传输，精确到分；不平衡、锁定期间、未知科目单独列出。
  • 原始账簿只读；修订只新增版本；调整只进入隔离模拟。
  • 每次调查固定账套、数据快照、规则版本和政策上下文；新资料使旧复核失效，历史底稿仍可查看。
  • 模型建议与确定性事实分开存储；引用必须真实存在、属于当前快照且已被读取。
  • 运行中的 Agent 只有只读的快照查询工具，不提供任意 SQL、代码或 Shell；预算用尽或输出无效都记为失败，不冒充成功。

3.2 运行方式与技术栈

本地模式：SQLite（WAL）＋单进程后台任务，无需 Docker 或模型密钥。部署模式：Docker Compose 编排 PostgreSQL、Redis、Celery 和 LangGraph 持久检查点，对外端口只绑定本机回环地址。前端为 Vue 3＋Naive UI 工作台，后端为 FastAPI＋Pydantic，接口契约由脚本从后端生成前端类型，CI 检查漂移。

主要开源组件均为直接依赖或可选组件，许可由 CI 门控逐一检查（见第 7 章）：FastAPI、Pydantic、SQLAlchemy、Alembic、LangGraph、OR-Tools、pdfplumber、PaddleOCR（可选）、BGE＋pgvector（可选）。

4 核心流程与功能

4.1 复核闭环

  1. 建立账套（企业会计准则或小企业会计准则，制度建立后不能原地更换）。
  2. 导入资料：CSV／JSON／XLSX、文本 PDF、财政部数电发票 XML 或扫描件（OCR 结果须人工逐字段核实）；先预览字段和错误，缺失金额不补零。
  3. 执行月结检查：{{json:release#rules.catalog_rules}} 条确定性规则生成案件（导入银行流水后含 {{json:release#rules.funds_rules}} 条资金核对规则），每条发现带来源记录和限制说明。
  4. 证据调查：规则模式不调用模型；模型模式需显式启动，且只能读取当前快照；调查结论只作参考，不改变处理分录。
  5. 处理草稿与隔离模拟：能确定的修正直接生成分录，只能确定金额方向的留空必填，无法确定的只列所需资料；程序在副本上复算余额并重新检查，列出本案发现是否消除和新引入的问题。
  6. 补证与接续：登记补证事项；新资料形成新快照后重新检查，同一发现接续到新案件，未再出现的发现生成接续核对案件，候选资料须人工确认。
  7. 复核与底稿：选择所依据的模拟方案，冻结当时的未决事项；导出含接续、补证、草稿与对比、未决事项的 Markdown／JSON 底稿；可选多用户模式下调查、复核、审批由不同账户完成。

4.3 政策检查与公开资料闭环

政策检查来自 32 份财政部企业会计准则实施问答，编成 33 条有限规则。每条规则记录官方原文链接与哈希、适用与不适用条件；依赖专业判断的条件必须由人工确认并引用当前快照的资料。财政部 2025 推广应用版数电发票标准包中的两份 XML 样例可以一条命令完成采集、核验投影、隔离 API 与浏览器验收和证据哈希汇总；另有标注明确的重复凭证教学变体，用于实训。

5 技术创新

项目不以“接入了多少模型或框架”作为创新，而是解决一个既有方案没有处理好的问题：让会计复核中的每一条自动化结论都能被第三方核验。下面五点都对应仓库里可复现的证据。

创新点做法证据
① 快照绑定的证据调查每次调查固定账套、资料、规则版本与政策上下文；引用必须属于当前快照且已被读取；迟到资料生成新快照，旧复核失效4 个独立时间挑战：保留快照时判断正确 4/4，混入后来资料时只有 2/4；端到端测试覆盖旧复核失效
② 模型提议与业务事实分离模型只能提出待复核的解释；处理草稿由案件发现确定性生成，进入隔离模拟，由程序逐分复算并对比前后发现6 份草稿（5 份有错）：程序复算拦住 4/5，直接采信建议则 5/5 全部放过；“合法科目间业务用途错误”仍会通过，作为已知缺口公开；场景包验收中 3 格经草稿模拟消除本案发现且未引入新问题
③ 官方问答驱动的可审计规则包32 份财政部实施问答编成 33 条有限规则，记录原文哈希、适用与不适用条件；专业判断一律人工确认{{json:policy#official_projection.passed}} 个手写投影全部通过；AI 审阅发现的范围问题逐条整改，旧版失败反例留档
④ 预注册封存评测评测真值不进入运行中的 Agent；封存数据只用一次；与同预算确定性基线对比；付费运行有费用守护v2、v3、v4 三次封存测试中单 Agent 均未超过基线（v3：0.508 对 0.563）；v4 混合方法高于单 Agent 但未超过最强基线，结果原样公开（见 5.2）
⑤ 可离线核验的交付证据一条命令完成公开样例采集、隔离 API 与浏览器验收和哈希清单；复制后的验收包可只用标准库核验验收前后核对 {{json:policy#public_delivery.stages.3.sources}} 份源码与配置、{{json:policy#public_delivery.stages.3.evidence}} 份证据；篡改副本被拒绝

5.1 为什么让确定性规则先判断

v3 封存测试的逐类结果显示，模型擅长依赖文字线索的原因（作废重开、价格折让），确定性方法擅长需要解读补证资料的原因（错挂发票号、货物在途）。两者互补，但直接让模型做最终判断，整体效果反而低于确定性方法。因此产品中，确定性检查与程序复算始终先于模型；模型只给出待人工复核的解释，不能直接成为结论。能否进一步用“规则能下结论就不调用模型”的混合方式提升效果，我们单独做了预注册检验，见 5.2。

5.2 混合方法的预注册检验（v4）

基于 v3 的观察，我们提出“确定性优先、模型兜底”的混合方法：规则触发且固定补证得出确定类别时直接采用确定性结论；否则交给单 Agent。该方法在任何 v4 模型请求之前已公开预注册（GitHub Issue #12、docs/ROOT_CAUSE_V4.md），在新生成的 v4 数据上检验五个目标（T1：宏 F1 比最强同预算基线高 0.05 以上；T2：增益的自助区间下界大于 0；T3：不低于单 Agent；T4：结构失败不超过 1；T5：每案请求不超过单 Agent 的 60%）。封存运行于 2026-10-22 按冻结计划完成，9 个场景族 × 3 次，未中断。

7 开源治理

7.1 许可与依赖合规

  • 自主代码采用 Apache-2.0，附 NOTICE 与引用信息（CITATION.cff）；没有复制 ERPNext、Odoo、Beancount 等第三方源码，ERPNext（GPLv3）只作为独立服务联调。
  • CI 的 licenses 作业逐一检查已安装 Python 依赖和前端锁文件条目：{{lic:summary}}。元数据含糊的包逐个读取随包 LICENSE 核对并记录依据；psycopg（LGPL-3.0，运行时动态库）和 beancount（GPL-2.0，仅可选评测）是写明理由和范围的例外。
  • 公开资料（财政部问答、数电发票标准包、年报等）只保存来源、哈希与转换程序，不重新分发原件；公开前对全部 Git 历史做了只读审计（{{json:audit#blobs_scanned}} 个对象，阻断项 0）。

7.2 贡献机制

  • 治理文件齐全：贡献指南、项目治理、行为准则（Contributor Covenant 2.1 中文版）、安全策略、维护者与支持说明；GitHub 社区健康度 {{gh:health}}%。
  • Issue 表单：缺陷、功能建议、数据来源提议，以及会计规则请求——必须填写官方来源、适用与不适用条件和独立回归案例，否则无法提交，把 AGENTS.md 的规则变更要求落到了入口。
  • 所有改动经 PR 合入，PR 模板要求写明已运行的测试、AI 参与和未验证事项；CI 必需检查全部通过才合并；Dependabot 每周提出依赖更新。
  • 截至 {{meta:date}}：{{gh:prs}} 个 PR、{{gh:issues}} 个 Issue，路线图拆分到 4 个里程碑。

7.3 质量门控

每次提交在全新机器上运行 {{gh:jobs}} 项 CI 作业：Linux 后端全量测试、可选依赖（PostgreSQL 迁移、pgvector 索引、Beancount 差分，任何跳过即失败）、许可门控、前端构建、按 README 原样启动（Linux 脚本、Windows 启动器＋Windows 后端全量测试、Docker Compose），以及重新生成合成数据、保持 480/30 规则契约并在空库中跑浏览器端到端测试。偶发失败不被隐藏，作为 Issue 跟踪（#33）。

8 长期发展

8.1 团队与维护方式

项目目前由一名学生负责，在 AI 编程助手（Claude Code、Codex）辅助下开发和维护。为保证一个人也能持续维护，项目把规则写成可执行的约束：AGENTS.md 规定协作底线（金额精度、原账只读、证据真实、失败不冒充成功、不改测试答案迁就实现）；GOVERNANCE.md 规定 AI 改动与人工改动一样必须经过 PR、CI 和维护者合并，付费模型调用须事先批准预算；交接文档、逐项验证记录和一键验收脚本降低了“只有一个人懂”的风险。

正在招募的角色：会计规则评审员（会计专业教师或注册会计师，负责把规则从 experimental 升级）、教学试点合作者、前端与文档贡献者。

8.3 可持续性

  • 本地优先：规则演示与全部测试不需要云服务或模型密钥，运行成本接近零。
