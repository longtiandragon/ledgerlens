# 原因调查评测轨道（root-cause-track-v1）

规则标签轨道（`benchmarks/run_agents.py`）让模型在不看规则结果的情况下从零复核，并以规则引擎按构造即可全中的规则标签计分；在这种口径下模型最多与规则持平，无法证明调查的增量价值。本轨道改为评测规划中的问题：在相同规则结果之上，方法能否得到正确的原因类别与结论，主动取得被扣留的资料是否有帮助。

## 定义

- **可见原因类别**（`CATEGORIES`，11类）：正常业务、重复入账、单据迟到、分录遗漏或借贷不平、科目映射、期间不一致、来源冲突、收货超额、确认金额不一致、缺发票、余额不衔接。方法只能在这些类别中选择。
- **结论**：沿用产品四类——证据支持、正常差异、证据不足、超出支持范围。
- **真值**：只由生成器的评测文件（`fault_mechanism`、`expected_rules`）经 `FAULT_CAUSES` 映射得到，不调用任何生产函数。每项映射都是对合成故障含义的书面判断，可复核。
- **结论随取证状态变化**：资料被扣留时，单据缺口的正确结论是证据不足；方法取得扣留资料后，缺口补齐，单据迟到属于正常差异。原因类别不随取证改变，未取证的方法因此拿不到“单据迟到”这一类别。
- **扣留资料释放**：只有结构化请求（资料种类，可选订单/发票/来源编号）匹配扣留记录时才释放，自由文本请求不释放任何资料；释放由评测器执行，运行方法看不到真值。
- **主指标**：原因类别 Macro-F1（多标签）、结论准确率，失败计入分母；另报告取证次数、无扣留资料时的多余请求和按场景族的自助区间。

## 基线结果（模型请求0次）

`python -m benchmarks.root_cause --split development --output <报告>`，汇总见 [root-cause-baselines.json](root-cause-baselines.json)。

|划分|方法|原因Macro-F1|结论准确率|取得扣留资料|
|---|---|---|---|---|
|开发集300例|仅规则|0.874|96.7%|0/40|
|开发集300例|规则＋固定取证|0.965|96.7%|40/40|
|验证集80例|仅规则|0.857|100%|0/20|
|验证集80例|规则＋固定取证|1.000|100%|20/20|

“规则＋固定取证”是确定性固定流程：只要出现收货缺口就请求收货单，取得后重新执行规则。开发集唯一未命中的是`partial_booking`场景族，没有规则能发现确认金额不足（该族按“确认金额不一致、证据支持”计入，属于评测者判断）。

## 结论与限制

当前合成数据中，几乎每种故障都与一条规则一一对应，固定取证流程已经接近满分。规划中“相对最强同预算对照提升至少5个百分点”的目标在这份数据上**无法被证明**，问题在数据集而非模型；继续在其上花费模型调用没有研究价值。

`identical_visible_two_causes`场景族对两种隐藏原因使用完全相同的资料，其释放资料又与单据迟到场景族一致，任何方法都不可能同时答对二者。该族位于封存测试集，本轨道将其单独报告、排除在主指标外；封存测试集未运行。

要检验主动补证或模型解读的价值，需要新的数据：同一规则信号对应多种原因，且区分原因的资料种类因案件而异、取证有成本，或关键信息只存在于非结构化文字中。设计这类数据时，必须同时提供同等强度的确定性或关键词基线，并在新的独立划分上验证。

## 数据集v2（root-cause-v2.0.0）与同预算基线

`python -m datasets.generate_v2 --output .local/datasets-v2`生成270例：9种原因 × 3个划分 × 10个变体。同一信号组内各原因的规则信号完全相同（重复发票组、收货缺口组、无规则信号组），区分原因只能依靠扣留资料或文字备注。每个原因在三个划分中使用不同的拓扑，**每个划分使用独立、互不重叠的措辞模板**；验证集和封存集的措辞是新写的，部分刻意避开开发集关键词。案例与场景族编号为不透明哈希，原因只存在于评测真值文件。所有文字为固定模板，没有由模型生成；模板在任何模型运行前确定。

|信号|原因|决定性扣留资料|
|---|---|---|
|重复发票|真实重复入账|无|
|重复发票|第二次交货错挂同一发票号|发票|
|收货缺口|单据迟到（期内收货）|收货单|
|收货缺口|货物在途（期后收货）|收货单|
|收货缺口|订单减少|订单变更（70%变体有备注提示）|
|收货缺口|无法判定|无|
|无信号|正常且有无害备注|—|
|无信号|发票已作废重开|发票（备注提示）|
|无信号|约定折让需冲减|红字发票（备注提示）|

所有方法每案最多一次结构化补证（种类＋可选编号），未匹配时返回明确的空结果；结论真值随是否取得决定性资料而定。三个确定性基线（`benchmarks/root_cause_v2.py`）：仅规则；规则＋按规则标签的固定补证及确定性解读（含收货日期判断）；关键词补证（关键词只取自开发集措辞）。

|方法|开发集 F1／结论|验证集 F1／结论|
|---|---|---|
|仅规则|0.146／77.8%|0.146／77.8%|
|规则＋固定补证|0.563／77.8%|0.563／77.8%|
|关键词补证|0.978／100%|0.625／81.1%|

关键词方法在其来源措辞上接近满分，在新措辞上降至0.625／81.1%，说明这份数据确实留有“理解文字并据此选择补证”的空间，可以用来检验规划的主动补证主张。需要注意：数据是为检验这一能力而设计的，结果只说明在该合成设定下的差异，不能外推为真实账套效果；验证集措辞由同一作者编写，可能带有作者偏好。封存测试集只在最终评测时运行一次。

模型方法通过真实调查图运行（`benchmarks/root_cause_v2_models.py`）：`root_cause`任务以全部确定性规则结果作为已验证事实，模型在`cause_assessment`中从可见类别选择原因，并可提出一次结构化补证；评测器释放资料后在新快照上进行第二轮且不再允许补证。提示版本`investigation-v24`。

## 封存测试集最终对比（2026-10-12）

配置在开发集冒烟后冻结（`investigation-v25` + `rc2-runner-v2`），封存测试集此前从未运行。每种原因1例共9例；因剩余预算，单Agent只重复2次（规划要求至少3次，未达到），确定性基线同样运行2次。103次付费请求，低谷价约¥1.55，报告`.local/reports/root-cause-v2-sealed-final.json`。

|方法|原因F1|结论准确率|取得决定性资料|失败|
|---|---|---|---|---|
|仅规则|0.146|77.8%|0/12|0|
|规则＋固定补证|0.563|77.8%|6/12|0|
|关键词补证|**0.688**|77.8%|8/12|0|
|单Agent|0.438|**38.9%**|5/12|**6/18**|

单Agent的原因F1低于固定补证和关键词补证，结论准确率约为确定性方法的一半（场景族自助区间0.17–0.61，确定性方法0.44–1.00）。18个样本中6个输出校验失败：引用快照外证据编号16次、claims缺少`rule_id`7次、补证编号不可见2次，19次校验事件中13次发生在第一轮。成功样本中仍有取得期后收货单却判为正常、取得资料仍判证据不足等推理错误。

结论：在本合成设定和当前接口下，“模型＋主动补证优于同预算确定性方法”的主张**未得到支持**，与规划的预注册目标相反。主要瓶颈之一是原因调查任务沿用完整调查输出契约（claims、hypotheses必须引用合法证据），模型常在结构与引用上失败；改用更窄的输出契约可能改善，但必须作为新版本在新数据上重新验证，不能回头对已用过的封存集调参。样本量小（9个场景族、2次重复），不足以排除小幅差异；结果不能外推为真实账套效果。按规划要求如实保留失败分析并调整技术主张：当前版本中，模型的作用应限定为在程序规则之上提供待复核的解释，而不是替代确定性判断。
