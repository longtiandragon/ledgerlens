# 调查中的已保存政策检查

调查版本 `investigation-v21` / `snapshot-tools-v11` 使用 `InvestigationPolicyContext` 保存运行启动时的政策上下文。它独立于原账簿、核心执行规则和已保存的政策检查，不创建分录或专业审批。

## 固定哪些资料

启动接口在账套锁内创建运行与上下文，同一事务保存后才派发任务。上下文固定账套、快照标识及摘要、捕获时间、政策规则包身份、当时最新版条件清单，以及这些条件已有的当前规则包检查。

最新版条件尚未检查时，清单仍保留该版本，检查正文留空，不退回旧版本的结论。每次最多保存60项检查；超限或来源校验失败明确拒绝，不能静默截断。捕获前重核验原始文件、确认导入映射和原行定位。同一快照历史条件和检查中的无效绑定也会拒绝此次捕获。

账务资料截止时刻、人工标注时刻与本次捕获时刻分别保存。人工在后来确认历史订单的用途，并不说明当时已知此判断。历史快照可以启动调查，仍使用那份快照的资料，界面单独显示版本过期状态。

Worker和恢复流程只载入本次保存的上下文。后续新增条件、替代版本或完成检查不会改写它。运行读取接口和底稿导出给出当前过期原因；这一状态不回填原载荷。旧运行没有捕获上下文时明确返回 `legacy_uncaptured`。曾经捕获的记录缺失或被移属不能伪装成旧运行。

## 模型怎么读取

`read_policy_checks` 只接受 `check_ids`，最多6个，不重复。空列表读取固定上下文的前6项，返回总数、可用编号和截断标志。正文包括保存结果、人工条件、原始来源定位及当前快照中的原记录。查询只读内存中的固定载荷，不访问当前数据库、网络、评测答案或新快照。

模型初始只看到编号索引，必须实际读取完整查询结果才能引用检查。共享记忆按检查编号保存正文，查询摘要绑定正文哈希。另一个角色的解释、索引或哈希均不能代替当前角色读取；`read_evidence_queries` 可以读取已有查询的完整正文。

主动选择器也可选择此工具；可用性和成本由服务端配置，模型不能增加权限。它仍是有界查询选择，不是经过校准的概率推理。

模型将政策解释放入独立 `policy_interpretations`：仅有文本与检查编号，服务端另标记解释语义未验证。核心 `Claim.rule_id` 不接受政策检查编号，政策解释不改变 `fact_status`，不成为已核验账务事实或自动调整。

## 界面与导出

调查室展示本次固定的条件、结果、来源及两种截止时间，注明人工确认和未决事项。原始来源可打开现有证据浏览器，金额保持字符串。条件和结果版本变化会显示历史回查提示。JSON和Markdown底稿按运行保存 `investigation_policy_contexts`，同时保留模型解释。

接口为 `GET /api/v1/runs/{id}/policy-context`。请求与响应由Pydantic生成OpenAPI和前端类型。迁移0003仅新增上下文表，0001和0002不改写。SQLite新环境迁移和PostgreSQL离线SQL检查不等于PostgreSQL实机验收。

## 验证边界

存储、工具、模型Mock流程和独立HTTP攻击测试用于验证冻结、引用、作用域、错误拒绝与读取约束；真实本地API验收使用明确标注的合成账套，模型请求为0。它们不能证明DeepSeek解释质量、多智能体增益或真实企业业务有效性。

上下文摘要用于内容一致性检查，不是抵御能同时替换本地文件、数据库和全部摘要的攻击者的签名系统。本轮不把政策条件变更绑定到专业审批或调整模拟；这些能力需要独立版本契约和验收。
